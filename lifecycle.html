STEP 03

STEP 04

STEP 05

· 时间占比 ·

同样是一次对话，时间花在哪不一样

Prompt 越长，Prefill 占比越高；输出越长，Decode 占比越高 —— 同一张显卡，在不同场景下"快"的定义完全不同。

· 阶段详解 ·

每个阶段，决定速度的因素不同

Prefill 是并行计算密集型，Decode 是显存带宽密集型 —— 这也是同一张 GPU 在两项跑分上表现不同的根本原因。

STEP 02
Tokenization
TEXT → TOKEN IDS

按分词器词表把文本切成 token，CPU 上完成，耗时通常在毫秒级，占比极小。

计算类型CPU · 轻量
占比通常 <3%
STEP 03
Prefill
PROMPT PROCESSING SPEED

全部输入 token 一次性并行送入模型计算，写入 KV Cache。属于计算密集型（compute-bound），吃算力和并行矩阵吞吐。

瓶颈算力 / 矩阵吞吐
Prompt 越长占比越高
STEP 04
Decode
TEXT GENERATION SPEED

逐个生成 token，每一步都依赖上一步的结果，无法并行。属于显存带宽密集型（memory-bound），吃 VRAM 带宽。

瓶颈显存带宽
输出越长占比越高
STEP 05
Detokenization
TOKEN IDS → TEXT

把模型输出的 token id 还原成可读文本，与分词一样是轻量级 CPU 操作。

计算类型CPU · 轻量
占比通常 <3%

网络传输
REQUEST / STREAMING

请求上行与逐块流式返回，局域网内通常可忽略，跨公网或高延迟链路会放大占比。

影响因素网络延迟
本地部署占比极小

· 关键指标 ·

评测报告里这些词到底在测什么

TTFT Time To First Token首字延迟 从发出请求到收到第一个输出 token 的时间，主要由 Prefill 速度决定
TPOT / ITL Time Per Output Token逐字延迟 生成每个后续 token 的平均间隔，即 Text Generation Speed 的倒数
吞吐量 ThroughputTokens / Second Prefill 与 Decode 分别有各自的 tokens/s，不能混用同一个数字
端到端延迟 End-to-End Latency总耗时 TTFT + 输出长度 × TPOT + 网络与分词开销
上下文长度 Context WindowPrompt + 输出总长 越长，KV Cache 越大，Prefill 占比越高，对显存带宽与容量要求越高
核心结论
Prefill 决定长文档 / RAG 场景的响应速度，Decode 决定长对话 / 长输出场景的流畅度 —— 选硬件前，先看清自己的场景更接近哪一种。
